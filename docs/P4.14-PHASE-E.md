## 2. 存储设计（STEP 2）

**不用 SQLite。** 一图一 sidecar + 原子 rename，足够，且「重启后还在」更容易验证。

```
.rc1-user-library/            ← .gitignore:28 已忽略，永不入仓
  images/<sha256>.webp        原始字节，按内容哈希命名
  records/u-<hash16>.json     一条记录 = 元数据 + 向量 + 版本指纹
```

| 决策 | 选择 | 理由 |
|---|---|---|
| 写入原子性 | 临时文件 + `renameSync` | rename 同卷原子，崩溃不会留下半条记录 |
| 内容哈希 | 原始字节的 sha256 | 解码后像素会随解码器版本变化，等于把同一张图判成两张 |
| 落盘文件名 | 内容哈希，**不采信用户文件名** | 从根上消除路径穿越与覆盖 |
| 删除顺序 | 先删记录，再删图 | 宁可留孤儿图，不留孤儿记录（孤儿记录会指向不存在的图） |
| 单条损坏 | 跳过该条并计入 `broken` | 一条坏文件不拖垮整库 |
| 版本不一致 | 计入 `stale`，检索时跳过 | **不静默混用** |

### 版本指纹

```js
VECTOR_FINGERPRINT = { model: "mobileclip_s0_vision_int8", fit: "pad", dim: 512, preproc: 1 }
// → "mobileclip_s0_vision_int8|pad|512|1"
```

模型、维度、预处理任一变化，旧记录自动落到 `stale`，UI 显示「N 张待重建」，检索不采用它们。**没有任何一条路径会在版本不一致时照样用旧向量。**

## 3. 增量索引（STEP 3）

- 导入**只算新增那张**：基础 47 条永远不重算。

- 候选池 = 基础 47 + 个人 N，**同一套 512 维、同一 `pad` 预处理**，维度天然一致。
- 删除时记录与图一起移除，下次检索不再出现。

## 5. 页面（STEP 5）

`experiment/p414/index.html`：**没有新建第二套前端**，就在原 A/B/C 页上加。

- **我的参考** 面板：批量选图 → 选分类（绘画 / 彩色电影 / 动画 / 日本动漫）→ 导入；缩略图墙；逐张删除；显示已导入数量与待重建数。
- **两种操作明确分开**：「用上传图片当查询」与「导入到我的参考」是两个不同按钮，互不干扰。
- 候选计数实时显示：`本次候选 55 张（基础 47 + 我的 8）`。
- 某分类为空就显示 0 条，不拿别的类别凑数。
- `?blind=1`：隐藏分数、相似点文案、以及会泄漏列含义的说明，只留图 + 标题/媒介/出处。

### 两个修掉的真实缺陷

**① 动画被算进「彩色电影」。** 动画的 `medium` 也是 `film`，原来只看 `kind`，选「彩色电影」会把动画一起列出来。现在 `film` 要求 `visualForm !== animation`。

**② 上传查询时 C 列是 B 列的副本。** 上传图的 `queryStructure` 原本只有 `aspect` 一个可比维度，低于组合检索的 4 维门槛，于是 `combined = similarity`，两列同序。现在上传图用 canvas **实测**明暗/饱和/冷暖（不猜），可比维度到 5 个，C 才真的在比。

## 9. 遗留问题

| # | 问题 | 说明 |
|---|---|---|
| 1 | 导入的标题默认取文件名 | 页面上没有逐张填「作品名/来源」的表单；任务书要求「可选填写」，目前只有分类可选 |

| 3 | 个人条目的影调维度为空 | 只有宽高比。若要影调，需要在导入时也算一次主色，本次未做 |
| 4 | 组合检索在可比维度 < 4 时退化为纯向量 | 这是设计（不让弱证据主导），但意味着某些查询 A/B/C 只有两列有区别 |
| 5 | 没有索引重建命令 | 版本变化会把旧条目标 stale，但还没有一条命令批量重算 |
| 6 | 动画/动漫仅靠**用户导入** | 开放来源依然没有合法动画帧（P4.14-B/C 结论） |
