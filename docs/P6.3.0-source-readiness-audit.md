## 1. Image input contract

### 1.1 现有输入通道

| 通道 | 入口 | 接受的输入 | 状态 |
|---|---|---|---|
| 浏览器上传 | `uploadService.uploadFromImage(file)` | `File` / `Blob`（浏览器对象） | 单用户、本地 |
| 字节上传 | `uploadService.uploadBytes(bytes, ...)` | `Uint8Array` + mime | **本阶段的关键入口** |
| 预处理 | `prepareVisionImage(file)` | 浏览器 `File`，canvas 缩放至 ≤1280px JPEG | 浏览器限定 |
| 服务端桥 | `POST /api/vision` | base64 data URL，6MB 上限，mime 白名单 | 同源 |

**审计结论**：输入契约是 **blob 导向**的，不假设来源。因此任何外部 source（博物馆 API / 公版剧照）只要能下载成字节，就能进入同一条链路。**无需修改。**

### 1.2 mime 白名单

`VISION_MIME_OK = { image/jpeg, image/png, image/webp, image/gif }` —— 三个博物馆的 IIIF/图片服务全部返回 `image/jpeg`，实测通过。

## 2. Metadata contract（Q2）

`src/services/memory/types.js` 的 `createVisualMemory`：

```js
metadata: {
  title: metadata.title ?? "",
  origin: metadata.origin ?? "",
  film: metadata.film ?? null,
  year: metadata.year ?? null,
  tags: Array.isArray(metadata.tags) ? [...] : [],
  createdAt: metadata.createdAt ?? "",
  ...metadata,   // ← 关键：允许任意附加编辑性字段，永不参与检索
},
```

对照 P6.3 要求的字段：

| 要求字段 | 契约支持 | 承载方式 |
|---|---|---|
| `sourceType` | ✅ 扩展键 | 或复用 `source`（MEMORY_SOURCES 枚举，见下） |
| `sourceName` | ✅ 扩展键 | `metadata.sourceName` |
| `sourceUrl` | ✅ 扩展键 | `metadata.sourceUrl` |
| `artworkId` | ⚠️ **无显式字段** | 建议用 `metadata.sourceId`（现有 adapter 已用此名），或 `artworkId` 作为扩展键 |
| `creator` | ✅ 扩展键 | `metadata.creator` |
| `year` | ✅ **显式声明** | `metadata.year` |
| `medium` | ✅ 扩展键 | `metadata.medium` |

**这是一个"够用但未显式声明"的契约**。由于 `...metadata` 透传，P6.3 无需改 `types.js`（那是冻结模块）。适配器统一输出 `sourceId` 而非 `artworkId`，与项目既有 adapter 命名一致。

### 2.1 `MEMORY_SOURCES` 枚举 —— 一个需要诚实指出的限制

```js
export const MEMORY_SOURCES = [
  "user-upload", "film-still", "photo", "ai-generated", "artwork-reference", "example",
];
```

`createVisualMemory` 对未知 source **抛错**。这意味着：

- 外部博物馆资产只能落在 `artwork-reference` 这一个值上
- 无法区分 `met` / `aic` / `rijks` 三个来源

**本阶段处理方式（不改冻结模块）**：来源标识放在 `metadata.source`（扩展键），`createVisualMemory` 的 `source` 参数统一传 `artwork-reference`。这样既满足枚举约束，又能按真实来源分组，且不碰 `types.js`。

> **这是本阶段发现的最重要的架构约束**：枚举封闭。若未来要让产品原生区分「我从大都会存的」与「我从 Rijks 存的」用于 UI 分组，需要用户授权后扩展 `MEMORY_SOURCES`。本阶段不需要。

## 3. Retrieval / Profile 字段隔离（决定 external source 能否进入同一空间）

**实测确认**（grep 全文）：

```
grep "metadata\." src/services/memory/retrieveVisualMemory.js  → 0 命中
grep "metadata\." src/services/memory/visualProfile.js→ 0 命中
```

检索与画像**只读 `visualIntent`**。这意味着：

> 外部来源的 title / creator / museum / year 等编辑性元数据**在物理上不可能**影响检索排序或画像统计。跨媒介统一空间不是靠约定保证的，而是靠字段隔离保证的。

**这是 Q2「外部资产是否进入同一视觉语言空间」的结构性答案：能，且只能。**

## 5. 外部 API 实测可用性（本阶段亲自探测，非引用旧文档）

### 5.1 Met Museum ——⚠️ **发现真实 API 迁移**

```
GET /public/collection/v1/search
→ {"message":"/public/collection/v1/search was retired on 2026-10-01.
            ... use /public/collection/v1.1/search, which is Elastic-backed
            and paginated via offset and limit."}
```

|端点 | 状态 |
|---|---|
| `/public/collection/v1.1/search` | ✅ 200，`{"total":34601,"objectIDs":[...]}` |
| `/public/collection/v1/objects/{id}` | ✅ 200（**未迁移**，仍在 v1） |
| `images.metmuseum.org/.../web-large/*.jpg` | ✅ 200，`image/jpeg`，221KB 实测 |

> **这是 P6.3 最有价值的一条实测发现**：项目内现有 `metAdapter.js` 若仍使用 v1 search，**在今天的线上环境已失效**。适配器不检查响应体中的 `message` 字段，会把错误当成"0 结果"。

### 5.3 Rijksmuseum

| 项 | 实测 |
|---|---|
| 搜索 | ✅ `https://data.rijksmuseum.nl/search/collection?imageAvailable=true&creator=X` → 200，`totalItems: 1447`，每页 100 |
| 分页 | ✅ `next.id` 内含 `pageToken`（**注意：`next` 是对象不是字符串**） |
| 解析 | ✅ `/{id}?_profile=edm-framed` → 200 |
| ⚠️ 其他 profile | `edm-full` / `ldjson` → **406 Not Acceptable** |
| ⚠️ 图片 URL | **顶层 `isShownBy.id` 才是真实可用IIIF URL** |

> **第二个实测发现的既存缺陷**：项目内 `rijksAdapter.js` 注释声称走 `https://iiif.micr.io/<imageId>/full/{w},/0/default.jpg`，但实测该拼接路径**返回 404**；真实 URL 由resolver 以 `isShownBy.id` 直接给出（如 `https://iiif.micr.io/hodeb/full/max/0/default.jpg`）。此外 `toRaw()` 把 `isShownBy` 从 `aggregatedCHO` 里取，而该字段实际在**顶层**。

实测成功的样例：
```

200107928 | The Night Watch Militia Company…  | Rembrandt van Rijn | 1642
```

## 8. STEP 1–5 的分层策略（因G6 阻塞）

本阶段必须在「无凭据」的现实下最大化验证深度。分三层，**每层都如实标注**：

```
第1 层  外部 source 接入与真实性   —— 完全可做（不需 vision）
         STEP 1 艺术数据库 100/500/1000

第 2 层  视觉语言是否产生           —— 分两种intent 来源，逐条标注
         STEP 2 外部艺术资产的视觉语言
         ├─ 2a 真实 vision intent（已有 45 条Core V1 缓存的博物馆画作）
         └─ 2b 规则回退 intent（intentFromArtwork()）—— 必须标注 rule-fallback

第 3 层  跨媒介/规模/后端决策       —— 可用第 2 层 intent 跑真实检索
         STEP 3 电影双路径  STEP 4 跨媒介  STEP 5 规模  STEP 6 后端决策
```

**关键诚实原则**：本报告可以证明「架构支持外部 source」与「外部资产是真实可溯的」，但在无凭据下**不能**证明「1000 张外部资产都产生了真实识图结果」。这一条会写进最终报告，不含糊。
