**一句话**：local-first 的**架构判断是对的，不需要推翻**；但「个人视觉记忆」这个定位天然要求**跨设备**，纯本地无法承载。需要的不是完整 SaaS，而是**一个只存图片与 intent、不做社交不做协作的轻后端**。

---

## 1. 为什么不是 A（继续纯 local-first）

### 1.1 纯本地的能力已实测成立

| 能力 | 状态 | 实测 |
|---|---|---|
| 单用户个人库 | ✅ | 167 条，检索 0.49 ms |
| 本地收藏 | ✅ | 105+442 张真实文件，105/105 哈希校验通过 |
| 导入导出 | ✅ | `visual-archive` v1 格式，`buildArchive` / `validateArchive` / `importPersonalArchive` 齐备 |
| 隐私 | ✅ | 数据从不上传（P6.2.1 / P6.3 全部验证在本地完成） |
| 引用隔离 | ✅ | `allInPersonalPool: true`，`foreignIds: []` |

### 1.2 但有两条硬伤

**硬伤一：图片存储不是 local-first 能承载的量级**

实测：

```
intent store（167 条）      320 KB      ← 微不足道
图片（442 张）72 MB      ← 1000 张约 169 MB
```

浏览器 localStorage 上限通常 5–10 MB，**连 100 张原图都放不下**。当前产品实际依赖 IndexedDB 或内存，**这是浏览器给的配额，不是产品设计的容量**。用户存到第 500 张时会遇到真实的天花板。

> 注意：intent 数据极小（320 KB / 167 条 ≈ 1.9 KB/条，1000 条约 1.9 MB）。**真正需要后端的是图片，不是 metadata。**

**硬伤二：产品定位与单设备互斥**

「个人视觉记忆系统」的核心承诺是**记忆的连续性**。P6.2.1 已证明同一查询在 A/B/C 三池返回不同结果——**答案来自个人历史**。但如果用户换一台设备，全部历史归零：

```
在笔记本存的 500 张默片参考 → 换到台式机 → 检索结果完全不同
```

这不是功能缺失，是**产品承诺被设备边界否定**。

## 2. 为什么不是 C（完整 SaaS）

完整 SaaS 意味着账号、云端渲染、多租户隔离、协作、计费、隐私合规（GDPR/个人信息保护法）。当前证据**不支持**任何一项：

| SaaS 前提 | 当前状态 |
|---|---|
| 已有真实付费用户 | ❌ P6.2 的真实用户测试尚未执行 |
| 已验证跨设备需求 | ⚠️ 逻辑上必然，但无实测 |
| 已验证协作需求 | ❌ 无任何证据 |
| 本地性能不足需上云 | ❌ **实测 0.49 ms，性能远不是瓶颈** |
| 存储成本已测算 | ⚠️ 169 MB/千张，单用户可承担 |

**上完整 SaaS 会把 80% 的工程量花在解决尚未存在的问题上。**

---

## 3. 为什么是 B（轻后端）—— 具体边界

### 3.1 只需要这三件事

| # | 能力 | 说明 | 优先级 |
|---|---|---|---|
| 1 | **Vision API 代理** | 密钥不能进浏览器。这是**当前唯一的硬性阻塞** | 🔴 P0 |
| 2 | **图片同步** | 用户自己的图片，跨设备可见 | 🟡 P1 |
| 3 | **intent 同步** | 仅 1.9 KB/条，1000 条约 1.9 MB，成本可忽略 | 🟡 P1 |

### 3.2 明确不做

- ❌ 账号密码体系（可用匿名设备配对 / magic link起步）
- ❌ 云端图片处理与识别（图片直传对象存储，识图仍走 P0 代理）
- ❌ 社交、分享、评论、推荐
- ❌ 协作与团队空间
- ❌ 计费与订阅

### 3.3 数据归属必须写死在设计里

> **图片与 intent 属于用户，不属于平台。** 导出永远是完整导出，删除即真删，可导出即带走。

这与 local-first 的诚实传统一致，也避开「用户被锁定」的最常见指控。

## 5. ⚠️ 最重要的排序判断

**后端不是当前最紧的事。**

P6.3 全阶段最硬的阻塞是：

```
VISION_API_BASE / VISION_API_KEY 全空
```

它导致的具体后果，逐条都有实测证据：

| 后果 | 证据 |
|---|---|
| 1000 张外部资产无法验证真实识图 | STEP 2 全部 100 条 intent 为 `rule-fallback` |
| 跨媒介 4/11 查询未达标 | 对照实验：film 池 `cool` 可用量恒为 0 |
| 静物画被「巨大空间」召回 | 规则只读文本关键词，看不见画面 |
| `emotion` 产出率仅 4% | 规则回退不产出该字段 |
| 画像被污染 | 孤立人物 53% → 23% |

**这五项全部指向同一个根因。** 补上凭据后，跨媒介、召回质量、画像准确性会同时改善——**而后端解决不了其中任何一项**。

### 建议执行顺序

```
P6.3.1  补 vision 凭据 → 外部资产真实识图      ← 唯一硬阻塞
            ↓
P6.3.2  修metAdapter(v1.1) / rijksAdapter(IIIF) ← 既存缺陷，已定位
            ↓
P6.3.3  导入外部资产时的画像污染提示             ← 本阶段新发现
            ↓
P6.4     轻后端（P0 优先做 vision 代理）        ← 本文档决策
```

## 6. 若选择 A，必须诚实告知的代价

如果决定继续纯 local-first，以下三点必须写进产品说明，不能回避：

1. **容量上限真实存在**：约 300–500 张原图后会遇到浏览器配额问题（intent 本身不是问题，图片才是）
2. **换设备等于换人**：视觉记忆不跟随用户
3. **vision 密钥无法安全放置**：要么用户自备密钥（体验差），要么没有识图能力

**这不是不能接受的取舍，但必须是自觉的取舍。**
