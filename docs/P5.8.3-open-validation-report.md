## 2. 核心答案：五链泛化是否成立？

**对三个用户各自建成的池，五链 100% 成立（chainHoldsOnBuiltPool: A=true, B=true, C=true）。**

| 用户 | 池构成 | 上传 | Profile | Search（3 案例） | Assistant |

| **B 艺术研究者** | 15 绘画 + 7 摄影 | 22/30 | 22 样本 · tendency | 8/8/8 hits · **绘画+摄影混合命中** | 3/3 能力 OK |

三条泛化证据：

1. **同查询不同池 → 不同答案**：相似「孤独/空旷」查询在 A/B/C 池的 top1 分别是 ua-24 / ub-04 / uc-01（三池互不相同）——检索结果由个人池内容决定，不是开发者数据库的回声。
2. **解释全程在场**：9 个检索案例（每池 3 案例 × 3 用户）全部命中且 100% 带 reasons——冻结的 REASON_LABELS 表对新素材（默片剧照 / 宋元山水 / FSA 纪实摄影）同样能产出「为什么找到」。
3. **诚实纪律自动生效**：C 池仅 19 条时，Profile 自动降级为「初步观察（observation）」而非强行给出倾向结论——产品诚实机制在真实新数据上正确触发。

跨媒介混合：B 池每个检索案例同时命中 artwork-reference 与 photo（艺术收藏→个人画像成立）；C 池的「电影+绘画+摄影」混合空间因配额墙只建成 19/54（见 §3），部分验证。

## 3. Infrastructure Limitation（如实记录，非产品缺陷）

上传环节遭遇 provider 上游配额墙：

- **失败两类**：① `VISION_TIMEOUT`（高密度大尺寸画作扫描 >120s 超时，集中在东方绘画）；② `VISION_INVALID_RESPONSE` 快速失败（约 100 次调用后，上游开始返回 502 auth，持续 >70 分钟未恢复——判定为日级配额/凭据冻结）。
- **失败闭包有效**：所有失败均持久化、错误码可见、重试路径就绪（`retry-and-post.mjs` 幂等，配额恢复后重跑即可补齐 A 1 张 / B 8 张 / C 35 张，并自动重跑三阶段后处理）。
- **C 池中断点**：quota 在 uc-22 起触发——uc-01..uc-21（全部电影 + 首张绘画）成功，其后绘画与摄影全数快速失败。同批摄影在 B 池成功过，证明失败与素材类型无关，纯属上游配额。
