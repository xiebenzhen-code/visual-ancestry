# P5.1.8 — Upload Reliability Audit（STEP 0，只读）

Date: 2026-10-01 · 只读审计 · 未修改任何代码 · 基于当前代码状态 + P5.1.7 真实测试数据

## 1. 当前上传链路（读码确认）

```
浏览器路径（uploadMemory, src/services/memory/uploadService.js）
  File → arrayBuffer → mime 校验 → ≤6MB 校验 → sha256
    → callVisionProvider(file)          # 冻结 bridge client（src/services/vision/visionProvider.js）
    → normalizeVisionIntent(res.raw)    # 冻结纯函数
    → createVisualMemory → addMemory    # 仅成功时持久化
    → {ok:true, memory} | {ok:false, error, memory:null}

Node/QA 路径（uploadFromImage → uploadBytes, 同文件）
  imagePath → readFile → ext→mime 校验 → ≤6MB 校验 → sha256 → base64
    → fetch POST {base}/api/vision      # 60s AbortSignal.timeout
    → normalizeVisionIntent(data.intent)
    → createVisualMemory → addMemory    # 仅成功时持久化
    → {ok:true, memory} | {ok:false, error, memory:null}

服务端（scripts/server.mjs handleVision — 冻结）
  6MB body cap → base64 校验 → import openaiProvider
  → 未配置 503 provider-not-configured
  → provider 调用失败/返回异常 → 502 {error:{code: reason}}
  → 成功 200 {ok:true, intent, latencyMs}
```

## 2. 真实失败地图（来自 P5.1.7 20 张实测：10 成功 / 10 失败）

### A — Vision 层（8/10 失败，占 80%）

| 失败现象 | 数量 | 链路表现 | 根因（冻结面） |
|----------|------|----------|----------------|
| `invalid-json` | 8 | 服务端 502 `{error:{code:"invalid-json"}}` → 客户端 `data.error.code`（Node）/ `res.reason`（浏览器） | provider 当次返回无效 JSON（P3.2 同类：502 invalid-json；Provider latency 波动） |
| 60s 超时 | 2 | 客户端 `AbortSignal.timeout` → `network-error` | provider 响应 >60s（已知 latency 8–72s 波动） |

→ **10 个失败全部源于 provider 当次波动**（Vision 层上游），**没有一个**是客户端校验/服务端路由/存储问题。这与 P3.2 校准（45/49 ≈ 92%）对照：同一 provider 在 P5.1.7 当次 50% 成功——**成功率随时间/负载波动，偶发失败是常态**。

### B — 服务层（0/10 失败归因）

- 客户端校验（mime/6MB）、服务端 base64/body 校验、存储 addMemory——**在 P5.1.7 全链路中零失败归因**
- `memoryRepository`（双环境）无状态概念但存储稳定；`addMemory` 幂等 upsert 已具备 retry 覆盖能力

### C — 产品层（10/10 失败都放大为产品问题）

| 产品缺口 | 现状（代码确认） | 后果 |
|----------|------------------|------|
| 失败即消失 | 失败路径 `memory: null`，**不持久化任何失败痕迹** | 图片信息丢失，用户不知道发生了什么 |
| 无状态 | 没有 pending/processing/success/failed 概念 | 上传是一次性黑盒行为 |
| 无恢复 | 无 retry 入口 | 用户只能重新选图→重新走完整流程 |
| 无批量 | 一次一张（UI 单文件 input） | 20 张 9 分钟全手工，中途失败即中断 |
| 错误不友好 | 暴露 `http-502`/`network-error`/`invalid-json` 等开发语言；浏览器路径把 `res.reason`（timeout/server/…）直接上抛 | 用户无法理解、无法行动 |

## 3. 代码级问题定位（读码确认）

1. `uploadService.js` **错误码不统一**：浏览器路径用 `res.error`+`res.reason`，Node 路径用 `data.error.code`/`http-XXX`——同一失败两种表示
2. 失败路径**双出口都 `memory: null`**——状态模型无从谈起
3. `uploadBytes` 与 `uploadMemory` 两段近乎重复的编排（浏览器复用冻结 bridge client，Node 直接 fetch）——改造需同步两处（不合并，保留浏览器对冻结客户的复用）
4. `types.js` `createVisualMemory` **强校验 visualIntent 必填**——失败条目目前无法创建（占位方案：冻结 `emptyVisualIntent()` 为合法空 intent，source:"empty"）

## 4. 修复方向（对应 STEP 1–4，此处只做判断）

- **状态模型**：`status: pending|processing|success|failed` + `error:{code,userMessage}`；失败也落库（image/sha256/thumbnail 保留）→ "图片存在、状态明确、原因明确、可以恢复"
- **错误分类**：统一内部 code（`VISION_TIMEOUT`/`VISION_INVALID_RESPONSE`/`VISION_UNAVAILABLE`/`NETWORK_ERROR`/`PAYLOAD_TOO_LARGE`/`UNSUPPORTED_FORMAT`/`NORMALIZE_FAILED`/`UNKNOWN`）+ 中文用户文案
- **手动 retry**：失败卡片"重新分析"→ 同 id 重新上传（Node 用 image.path；浏览器用 thumbnail 降级或重选文件）→ `addMemory` upsert 覆盖
- **批量**：多选 + 队列 + 实时进度（完成 x/y、成功/失败/处理中）——不引入任务系统
- **不做**：自动无限重试、修改 Vision 核心、引入数据库、复杂任务系统

## 5. 结论

**真实失败地图**：

```
上传失败 100% 发生在 Vision 层（provider 当次波动：无效 JSON / 超时）
         ↓ 产品层 0% 吸收（无状态、无痕迹、无重试、无批量、错误不可读）
服务层 0% 归因（校验/路由/存储均稳定）
```

→ 修复的本质不是"让 provider 不再失败"（冻结面，不可控），而是**让失败可见、可解释、可恢复**——把"上传工具"变成"可管理的视觉资产入口"。
