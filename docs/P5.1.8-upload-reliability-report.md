# P5.1.8 — Upload Reliability MVP Report（STEP 7 可行性报告）

Date: 2026-10-01 · **Status: P5.1.8 UPLOAD RELIABILITY READY** · 产品层放心上传 · 失败不丢失 · 大批量可管理

> 关于本阶段的定位：**不解决"provider 为什么会失败"（冻结面，不可控），而是解决"失败之后怎么办"——让失败可见、可解释、可恢复**。
> 全程未修改任何冻结组件；未引入数据库、未引入任务系统、未修改 Vision 核心/检索/评分/缓存。

---

## 0. 一句话结论

**问题来源确凿（provider 当次波动，成功率随时段漂移）、技术手段成立（状态模型 + 分类 + 手动 retry + 批量的离线与真实双验证）、产品价值闭环成立（首传 90%，一次手动重试后 100% 恢复，失败零丢失）**——上传可靠性不再是使用前障碍，原计划下一阶段（P5.2 Personal Retrieval MVP）可以进入。

## 1. 问题来源（STEP 0 审计 + STEP 6 回测双重确认）

### 1.1 真实失败地图（审计）

P5.1.7 的 20 次真实调用，10 次失败全部归因 **Vision 层 provider 当次波动**：

| 失败现象 | 数量 | 归因 |
|----------|------|------|
| `invalid-json`（provider 返回无效 JSON） | 8 | provider 当次异常（冻结面） |
| 60s 超时 | 2 | provider 响应 >60s（latency 8–72s 波动） |

- 服务层（校验/路由/存储）**0 归因**
- 产品层 **10/10 放大为产品问题**：失败即消失（`memory:null` 不落库）、无状态、无重试、无批量、错误不可读

### 1.2 回测证实：失败与素材无关，是时间/负载函数

| 素材 | P5.1.7（当时） | P5.1.8（本次） |
|------|----------------|----------------|
| ruv-a04 | 失败 invalid-json | 首传失败 invalid-json → **retry 成功** |
| ruv-c12 | **成功** | 60s 超时 → **retry 成功** |
| ruv-c01/c02/c04/c06/c07/c10/c13/c16 | 失败 | **全部首传成功** |

→ 同一张图不同时段结果相反（ruv-c12），失败集前后完全不重叠——**任何"修素材/修客户端"的方向都无意义，唯一可控的是失败后处理**。

## 2. 技术可行性（实现 + 验证）

### 2.1 实现内容（全部个人层，零冻结修改）

| 层 | 改动 | 文件 |
|----|------|------|
| 契约 | `status: pending\|processing\|success\|failed` + `error:{code,message,retryable}`；failed 用冻结 `emptyVisualIntent()` 占位（source:"empty"，永不参与检索） | `src/services/memory/types.js` |
| 服务 | `UPLOAD_ERRORS` 8 类统一分类（4 类 retryable + 2 类用户输入不可重试 + VISION_UNAVAILABLE + UNKNOWN）；失败**持久化**为 failed 条目（保留 image/sha256/原图路径/缩略图）；`id` 参数支持重试 upsert | `src/services/memory/uploadService.js` |
| UI | 失败卡片（红徽章 + 中文错误 + 「重新分析」）；批量上传（多选 + 队列 + 实时进度 x/y·成功·失败·处理中 + 逐项重试）；详情页失败分支；索引失败计数 | `src/pages/memory.js`、`src/components/memory/memoryCard.js`、`src/styles/memory.css` |

### 2.2 离线 QA（零 mock、零 provider，`qa/memory/upload-reliability-test.mjs`）

**29/29 PASS**：

- **Case 1 正常上传**：bytes → success VisualMemory，metadata/note 零泄漏进 visualIntent
- **Case 2 Vision 失败**（502 invalid-json）：不产生伪造成功资产；failed 条目持久化；占位 intent `source:"empty"`（非检索材料）；错误码/中文文案/retryable 三态正确
- **Case 3 Retry**：失败 → 同 id 覆盖 → success；旧 error 清除；upsert 不重复
- **Case 4 批量混合**（10 张：6 成 4 败交错）：逐张状态与脚本一致；failed 全部带分类错误；success 全部真实 intent

### 2.3 真实回测（STEP 6，同素材同 bridge 真实 provider，`work/p5.1.8-store` 隔离）

| 指标 | P5.1.7 基线 | P5.1.8 MVP |
|------|-------------|------------|
| 首传成功率 | 10/20 = **50%** | **18/20 = 90%** |
| 手动 retry 恢复率 | 无（无重试机制） | **2/2 = 100%** |
| 终态成功率（含重试） | 50% | **20/20 = 100%** |
| 单张平均耗时（首传） | ~21s | ~28s（含最慢 59.6s） |
| 用户操作成本 | 20 张全手工、失败 10 张需重选图 | 选中 20 张 → 点一次「分析并保存」→ 失败 2 张各点一次「重新分析」 |

> 注：本次首传成功率 90% 高于 P5.1.7 的 50%，是 provider 当日波动所致（同 provider）。**可靠性 MVP 的正确衡量不是"首传率变了多少"，而是"失败后能否低成本恢复"——本阶段把 50% 失败从"致命摩擦"降为"一次点击"**。

### 2.4 用户体验 Test Case（真实链路，P5.1.5 已验证上传成功路径；失败/重试行为由离线 QA 覆盖——浏览器 DOM 点击级交互在本环境受 Chromium 不可用限制，诚实声明见 §5）

## 3. 产品可行性

### 3.1 验收对照（用户指令验收标准）

| 验收项 | 结果 |
|--------|------|
| 产品层放心上传 | ✓ 批量多选 + 实时进度；上传不再是一次性黑盒 |
| 失败不丢失 | ✓ Vision 失败落库为 failed 条目（图/哈希/路径/缩略图保存），即使关掉页面重开仍在档案里 |
| 大批量可管理 | ✓ 50 张安全上限、队列逐张、状态可见、失败项可单独重试 |
| 错误可读可行动 | ✓ 8 类分类 + 中文文案（如「AI 分析超时，请重新尝试。」），用户知道发生了什么、能做什么 |

### 3.2 产品语义变化

- **之前**：上传 = 「成功(!) 或 消失(?)」的二元黑盒；失败即数据丢失
- **现在**：上传 = 「成功 / 失败（可见可解释可重试）」；收藏动机的保护——用户不再因为 50% 失败而放弃收集（P5.1.7 Q1 结论中的最大使用前摩擦已消除）

### 3.3 成本

- 新增存储负担：每条 failed 条目与 success 同构（含占位 intent），体积增量可忽略
- 新增交互负担：无（重试按钮与删除按钮同等级，不强制）
- 无新增后端/数据库/任务系统依赖

## 4. 风险

| 风险 | 等级 | 说明 | 缓解 |
|------|------|------|------|
| provider 波动仍不可控 | 中 | 首传率随时段漂移（50%–90% 已见）；重试也可能失败 | 不做自动无限重试（产品控制）；一次手动重试是当前承诺；失败永不失（可再试或删除） |
| 浏览器降级重试质量 | 低 | 档案页重试用已存缩略图（≤420px JPEG）替代原图，分析质量可能低于原图 | 上传页失败项直接用原文件重试（质量无损）；档案页仅无原文件时的降级路径；卡片已诚实呈现 |
| 批量上限硬截断 | 低 | 单次 >50 张静默截断 | UI 提示上限；真实使用（20 张）远低于上限 |
| `pending/processing` 仅内存 | 低 | 页面刷新后处理中状态消失（不持久化） | 符合契约（契约只保证 success/failed 持久化）；刷新后 failed 仍在档案 |
| 契约扩展波及 | 低 | status/error 新增字段对旧数据（无 status 的历史记录）向后兼容（读作 success） | validate-memory-contract 已扩展校验；实例库未见旧格式 |

## 5. 诚实声明（本阶段限制）

- **浏览器 DOM 点击级验证仍受环境限制**（agent-browser/Chromium 在本环境 SIGTERM 不可用）：失败卡片、批量队列交互、重试按钮的**真实点击行为未经浏览器验证**——已由以下覆盖：构建产物核验（P5.1.5 TC1–TC3 真实链路）、离线状态机 QA（29/29，受控传输）、Node 真实回测（STEP 6，真实 provider）。
- **回测用 Node 路径**（`uploadFromImage` 直连 bridge）而非浏览器路径（`uploadMemory` 复用冻结 `callVisionProvider`）——两条路径共享同一错误分类与持久化逻辑，分类差异（`classifyBridge` vs `classifyHttp`）已由离线 QA 覆盖浏览器路径的 reason 映射。
- 当前模型不支持读图：不提供对任何素材的像素级评价，所有数据均为链路真实输出。
