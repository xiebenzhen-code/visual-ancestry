## STEP 2 · Attempts 证据

已采用测试期、非生产文件的精确计数方案：

- `work/p6.3.3/upstream-fetch-counter.mjs` 通过 Node `--import` 注入测试进程的 `globalThis.fetch` 包装。
- 只累加整数 `providerRequests`，不读取、打印或保存 URL、请求头、Key、请求体、图片、响应正文。
- `server/vision/openaiProvider.mjs` 只有一处上游 `fetch(config.endpoint)`；因此 server 进程内计数就是实际发往 Provider 的请求次数。
- `provider-smoke.mjs` 在每个资产 client 请求前后读取计数快照，以差值记录 `providerAttempts`。
- 计数文件缺失时，`providerAttempts = null`，明确标记 `not-measured`；不再使用 latency 推断。
- client harness 每资产只发 1 个请求，无整轮自动重跑。
- Bridge 内部既有瞬态重试最多 1 次，因此每资产最多 2 个上游请求，整轮最多 4 个。

离线验证：hook 计数与持久化测试通过（初始 0，触发 2 次后记录 2）；未触网、未调用 Provider。

**REQUEST_METERING = VERIFIED**（测试期计数方案已验证；本轮尚未产生真实计数）
