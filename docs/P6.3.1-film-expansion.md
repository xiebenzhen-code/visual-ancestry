## 4. 我的下载器缺陷（根因与修正）

### 4.1 缺陷

```js
// 原来只验证：真实图片 + 有来源
const dl = await materializeRecord(record, dest);
if (!dl.ok) return { ok: false, reason: dl.reason };
```

**缺少「内容是否属于目标类别」的校验。** Commons 的 `generator=search` 是全文搜索，不是分类检索 —— 搜「The Grapes of Wrath 1940」会返回任何含这些词的文件。

### 4.2 正确做法（本阶段已补）

两步策略：

1. **搜索时**：`gsrsearch` 加 `incategory` 或用 `File:` 前缀精确标题，减少噪声
2. **下载后**：按 caption 分类，非剧照**记录但不计入**（本阶段 `audit-film-stills.mjs`）

更好的做法是**人工确认清单**：先只探测、输出候选 caption，人工过一遍再下载。**批量盲下 95 张再筛是低效且不诚实的。**

## 5. 达标的路径

当前 79 张（61 存量 + 18 新增），差 21 张。可行方向：

| 方向 | 可行性 | 说明 |
|---|---|---|
| **Internet Archive 公版电影** | ✅ 推荐 | 那里有完整的公版默片拷贝，可直接取帧（需 ffmpeg，本环境**没有**） |
| **Wikimedia 精确标题检索** | ✅ 可行 | 用 `intitle:` 或已验证的确切文件名，避免全文搜索噪声 |
| **放宽到「1929 年前美国默片」** | ✅ 可行 | 公有领域范围明确，Commons 上这类文件质量高得多 |
| 商业授权片库 | ❌ | 法务与成本，本阶段不碰 |

**若继续推进，我建议先用「精确标题 + intitle 检索」重跑一轮**（成本约 5 分钟），而不是放宽标准接受存疑条目。

## 8. 这对 P6.3.1 意味着什么

STEP 8 门槛「真实电影截图 100+」**从「⚠️ 下载中」变为「❌ 79/100」**。

这**不改变整体判定** —— 闸门依然因 vision 凭据 NOT PASSED。但它新增了一条独立的缺口：**电影素材的精确检索能力不足**。

**诚实的结论**：Wikimedia Commons 的全文搜索不适合批量获取「特定电影的真实截图」。P6.4 若需要稳定的电影素材来源，应转向 Internet Archive 的公版默片（但需 ffmpeg 抽帧能力）或建立人工确认的片单。
