## 3. Request-Parity Diff（判定核心）

### 3.1 请求侧：15/15 完全一致

| 参数 | 值 | bridge vs direct C |
|---|---|---|
| endpoint | `ciyuan.glmtk.top/v1/chat/completions` | 同 |
| model | `glm-5.3` | 同 |
| **图像文件** | `monk-by-sea/detail.webp`（515 552 B）| **同** |
| mime | `image/webp` | 同 |
| `detail` | `low` | 同 |
| `temperature` | 0 | 同 |
| `max_tokens` | 800 | 同 |
| `response_format` | `json_schema` + `strict:true` + `buildSchema()` | 同 |
| SYSTEM_PROMPT | 7 条硬性规则 | 同 |
| USER_TEXT | 同一句 | 同 |

**没有任何 payload 差异。** schema 与 prompt 的复刻一致性已逐项核验
（`ENUM_FIELDS` / 两组TOKEN / `MAX_LIST_ITEMS` / `SYSTEM_PROMPT` 7 条 / `USER_TEXT` 全部 MATCH）。

### 3.2 结果侧：完全相反

| 路径 | HTTP | 延迟 | finish_reason | content | tokens | schema |
|---|---|---|---|---|---|---|
| **direct C** | 200 | 42 017 ms | `stop` | **611 B** | **749 / 800（93.6%）** | **valid** |
| **bridge** | 502 | 47 876 ms | — | **空** | — | — |

### 3.3 假设：`max_tokens` 临界占用

**状态：`STRONG_HYPOTHESIS` —— 尚未确认，不得标记为 CONFIRMED。**

glm-5.3 是**推理模型**，返回的 message 含 **`reasoning_content`**：

```
messageKeys: ["role", "content", "reasoning_content"]
```

`reasoning_content` 与 `content` **共用 `max_tokens = 800` 预算**。

- **direct C**：`completion_tokens = 749/800`，content 恰好写完（611 B）→ 成功
- **bridge**：推测 reasoning 略长一点 → 800 用尽 → **content 被截断为空**
  → `empty-response` → 502

**为什么只是假设**：上述解释完全建立在 direct C 的 `usage` 之上。
**bridge 失败响应本身没有任何 token / finish_reason 证据** —— bridge 只暴露
`{ok, intent, latencyMs}`（`server.mjs:121`），失败时连这都没有，
`usage` 与 `finish_reason` 全部不可见。

| 已知（direct C） | 未知（bridge 失败侧） |
|---|---|
| `completion_tokens = 749` | `completion_tokens` |
| `finish_reason = stop` | `finish_reason` |
| `reasoning_content` 存在 | `reasoning_content` 长度 |
| `content = 611 B` | content 长度（已知为空） |

**因此「bridge 那次也用满了 800」是推断，不是观测。**
另一种同等成立的解释：模型在该次采样中reasoning 恰好短于 content，
或上游存在采样随机性导致未达上限即中断。

**确认方式**：固定同一张图做 D1/D2 对照（`max_tokens` 800 vs 1600，
其余参数逐项相同）。见 §3.5。

> 历史校准只能说明「这类失败反复出现」，**不能证明其成因**：
> `qa/vision-calibration-results.json` 63 次中 47 成功，
> 16 次 502 里 **15 次是 invalid-json / empty 类**。
> 它证明症状反复，**不证明症状由 max_tokens 造成**。

### 3.4 排除的其他假设

| 假设 | 排除依据 |
|---|---|
| timeout（painting） | 47.9 s 在 60 s 预算内，单次返回 `empty-response` |
| timeout（film） | 83.4s 总耗时；逐次 timeout/retry 仍待证据，不能排除 |
| 认证 | 同一 key，direct C 通过 |
| payload 差异 | §3.1 逐项 15/15 一致 |
| provider 无 structured output | direct C schema-valid，22 keys |
| 图像本身不可读 | 同一张图 direct C 成功 |

### 3.5 待验证：D1/D2 对照实验

单变量对照，**同一张图**、除 `max_tokens` 外全部参数逐项相同：

| 探针 | `max_tokens` | 观测项 |
|---|---|---|
| **D1** | 800（= 当前 bridge 值） | status / latency / choices / `finish_reason` / **`completion_tokens`** / **`reasoning_content` 存在与长度** / content 长度 / schema validity |
| **D2** | 1600 | 同上 |

| D1 / D2 观测 | 结论 |
|---|---|
| 任一非200或 transport error | INCONCLUSIVE |
| D1有效usage、明确length且content空；D2更高上限、stop、非空且schema-valid、completion_tokens严格大于D1.maxTokens | STRONG_SUPPORT，仅支持本次direct探针预算效应 |
| D2成功且用量不超过D1上限，或两者成功 | PLAUSIBLE_NOT_PROVEN；不能排除D1曾耗尽预算 |
| R1、近上限用量、D2空或超时 | INCONCLUSIVE，不证明或否定单因解释 |

R1包含非对象JSON及一般格式错误，不能等同于截断。两次direct请求不能恢复历史bridge请求的usage或finish_reason，也不能确认历史bridge根因。后者继续UNCONFIRMED。

## 4. 附带发现：provider-smoke 的判定器已失效

`work/p6.3.1c/provider-smoke.mjs:180`：

```js
row.schemaValid = !!(intent && intent.source === "vision" && present.length >= 6 && unknown.length === 0);
```

**`buildSchema()` 只产出 22 个字段，不含 `source`。**
`source: "vision"` 是浏览器侧 `src/services/vision/normalizeVisionIntent.js:49`
注入的，**bridge（`server.mjs:121`）原样透传、不注入**。

| SCHEMA_FIELDS 多列 | 后果 |
|---|---|
| `composition` / `geometry` / `source` | `unknown.length !== 0` → `schemaValid` 恒为 false |

**即使 provider 完美返回，也会被判定为失败。** 本轮两张FAIL 走的是
HTTP 502 分支，未触发此缺陷；但一旦上游转为 200，该判定器会给出假阴性。

> 这与已登记的 `docs/P6.3.1-schema-validation-gap.md` 同源：
> bridge 只透传不校验，下游却假设它已归一化。

## 5. B 的 TIMEOUT 单独登记

```
label   : B.painting+plain
status  : null（未收到响应）
latency : 120 007 ms
transportError : timeout after 120000ms
分类    : PLAIN_MULTIMODAL_REQUEST_TIMEOUT
```

**不作为 multimodal 能力证据**（C 在携带同一张图时 PASS，已直接证伪）。

**观测事实**：B 在 120 000 ms 内未返回任何响应（`status: null`）。

**HYPOTHESIS / possible explanation（未观测，不作事实）**：
一种可能的解释是 plain text 缺少 schema 约束时模型 reasoning 更长
（无结构化输出可依），因而撞上 120s 预算。

> **该解释未经验证。** B 的超时响应中**没有任何 `usage` / `finish_reason` /
> `reasoning_content` 数据** —— status 为 null，响应体不存在，
> 因此 reasoning 的实际长度**无从观测**。
> 「reasoning 失控」目前是推测，不是观测结果。
>
> 可观测的相关事实仅有一项：C（**有** schema 约束）耗时 42 017 ms 完成。
> 单凭这一项**不足以**证明 B 超时的成因。

对比说明：C 与 B 的差异（有无 schema 约束）与结果差异（42s 完成 vs 超时）
**同时出现**，但**不能据此断定因果** —— 还存在其他未排除的变量
（如采样随机性）。二者都**不是**「模型不支持图像」。

## 6. 判定

```
PROVIDER_GATE = NOT_READY
BRIDGE_DIRECT_OUTCOME_DIFFERENCE = CONFIRMED
```

依据判定表：direct C PASS 但 bridge painting FAIL → `BRIDGE_DIRECT_OUTCOME_DIFFERENCE`。**（事实层，已确认）**

**但成因尚未确认。** 请求预算（`max_tokens=800` 对推理模型偏低）
是目前最强的解释，但仍属 `STRONG_HYPOTHESIS`：
其证据**全部来自 direct C 的成功路径**，bridge 失败侧没有任何
`completion_tokens` / `finish_reason` 观测值。

D1/D2 即使支持预算效应，也不确认历史 bridge 根因；
也**不得**据此改动生产 bridge。

按指令，**不进入 60-item validation**。
