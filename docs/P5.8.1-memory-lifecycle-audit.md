# P5.8.1 — Memory Lifecycle Audit（STEP 0 · 只读）

> 目标：确定生产版本 Personal Memory 的真实生命周期。本 STEP 零代码修改。
> 结论先行：**无 BLOCKER，可进入实现**——生产持久化在位、图片所有权可判定、无现行容量故障、portability 完全缺失（本阶段要补的正是它）。

## A. Production Store

**浏览器真实产品**使用 **localStorage，键 `visual-memory:v1`**（`src/services/memory/memoryRepository.js` L19/L27-80）：

- 结构：单条 JSON `{version:1, memories:[VisualMemory...]}`，每次 add/delete **全量重序列化整库**
- 模块级 `browserCache` 内存缓存 + 每次 mutation 尝试 `setItem`；`setItem` 失败（隐私模式等）时静默降级为**仅内存**（有丢失风险，见 Failure Modes）

**Production vs QA 必须区分**：
- `MEMORY_STORE_DIR`（Node `memories.json`）是 **QA / 演示 store 机制**，不是生产存储证据——本审计不将其计为生产能力
- 浏览器判定：`typeof window !== "undefined" && window.localStorage` → browser 分支；否则 node 分支

## B. Persistence Semantics

| 场景 | 结果 | 证据 |
|------|------|------|
| page reload | ✅ 存活 | localStorage 持久 + `browserStore()` 每次从 localStorage 重建（browser-store-test 6/6 以新模块实例模拟 reload 验证） |
| tab close/reopen | ✅ 存活 | 同上（localStorage 生命周期） |
| browser restart | ✅ 存活 | localStorage 持久化语义（磁盘-backed）；无代码级障碍 |
| dev server restart | ✅ 不影响 | 存储在客户端，服务端无状态 |

风险（非阻断）：隐私模式 / quota 满 → `setItem` 静默失败，数据仅存内存（L51-55 catch 空块）——本阶段 export 能力正是对此的第一道保险。

## C. Image Ownership（关键事实）

**用户上传图片**：
- `image` 字段只存 `{path: 文件名, mime, sha256}`——**原图字节不持久化**（字节仅经 `/api/vision` bridge 转发后丢弃）
- 唯一持久化的图像数据 = `userData.thumbnail`：上传页 `makeThumbnail()`（memory.js L514-534）canvas 缩至 **420px JPEG data URL（质量 0.72）**，刻意设计「keeps localStorage small」
- 即：**可恢复的视觉记忆 = 结构化数据 + 缩略图**，不是原图。这是既定产品设计（非缺陷），但 Archive 契约必须携带 thumbnail，且需向用户明示「导出含缩略图，不含原图」

**远程参考图片**（artwork-reference 来源）：`userData.thumbnail` 可能是远程 URL（museum CDN）或复用 thumb——import 必须容忍 URL 型/缺失型 thumbnail，不得假设全部为 data URL。

## D. Capacity Assessment

- 实测：41 条 QA 条目（**无缩略图**）序列化 = **60 KB**
- 估算（真实生产形态，每条带 ~40KB 420px 缩略图 data URL）：**~40 KB/条** → localStorage 典型配额 5MB ≈ **~127 条**
- 判定：对当前验证规模（34–40 条）**无现行 quota 故障**（无 BLOCKER C）；设计上支撑数百条级别的个人库；数千条原图级库需要 IndexedDB 迁移——**属后续 Gate，不在本阶段**。`navigator.storage.estimate()` 为浏览器-only API，列入真实产品生命周期测试项

## F. Data Boundary

清空 Personal Library **只允许删除** `visual-memory:v1`（browser）/ `MEMORY_STORE_DIR/memories.json`（QA）。

**必须保留、不得触碰**：
- Artwork cache：`src/data/visual-intents/artworks.json`（冻结数据文件）+ artService 搜索缓存（独立 localStorage key，24h TTL）
- `src/utils/profile.js` 的 STORAGE_KEY——**#eye 浏览行为画像**，与 Personal Memory 是 P5.3.0 审计确认的并存不合并关系
- QA fixtures（examples.json 等）、application assets、external reference cache

## Failure Modes（现状）

1. 隐私模式 / quota 满 → setItem 静默失败 → 会话内可用、重启丢失（无任何用户可见警告）
2. 误清浏览器数据 → 个人库永久消失（无导出无备份）——**本阶段的核心动机**
3. 原图不可恢复（仅缩略图）——产品事实，契约需向用户明示

## Minimal Implementation Decision

- **方案：JSON 单文件 Archive（无 ZIP）**——40KB/条 × 数百条 = 单文件数 MB，浏览器下载/文件读取均可承载；ZIP 引入依赖，违背最小原则
- **新增** `src/services/memory/archivePortability.js`：`buildArchive(memories)` / `exportPersonalArchive()` / `importPersonalArchive(archive, {mode})`（merge=upsert by id / replace=清后导入；逐条校验、坏条目跳过并报告）
- **最小修改** `memoryRepository.js`：新增 `clearPersonalMemory()`（browser: remove key + 重置缓存；node: 重写空 store）——属授权的「repository persistence adapter」最小修改，不动其余 API
- **最小 UI**：#memory 页新增导出/导入/清空控件（授权范围内）
- **恢复一致性测试**：import 后调 retrieveVisualMemory / buildVisualProfile 验证检索与画像恢复一致（调用不修改）

## STOP GATE 检查

- BLOCKER B（图片本体位置不明）：**未触发**——已明确：原图不持久化，唯一图像资产 = 420px data-URL 缩略图
