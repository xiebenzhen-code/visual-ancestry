# P5.9.0 — STEP 2 External Reviewer Simulation（三评审 · 结构化模拟）

> 诚实声明：与 P5.8.2 同纪律，本模拟基于真实 UI 代码路径与真实数据走查，不能替代真人评审；真人评审问题清单留白于文末。

---

## Reviewer A · AI 工程师

**走查路径**：README 级架构页 → architecture.svg → 冻结文档清单 → P5.8.4 grounding 数据。

**理解点**：
- 架构合理性：Local-first（原图不持久化、浏览器 localStorage / Node file store 双环境）、同源 `/api/vision` 代理（浏览器 bundle 零凭据）、规则式检索（VisualQuery + REASON_LABELS 解释层）——**无 embedding、无向量库**，依赖是显式的。
- **不过度 Agent 化**：Assistant 是 130 行级薄层（三个任务函数 + 规则映射表），无 Agent Loop、无自治循环、无工具调用链；`runAssistant({task, query})` 纯分派。grounding 校验显示全部引用 ∈ 个人池（泄漏 0）——「检索增强」而非「自由生成」。
- 冻结纪律可信：V2 基线 9 文件 + P5.8.1 基线 15 文件 sha256 全程完好，八个阶段零冻结面破坏。

**疑惑点**：
1. 规则式检索的召回上限——REASON_LABELS 是人工枚举，长尾视觉关系覆盖不了（产品已诚实标注 unmapped 收集）。
2. vision provider 是单一 OpenAI 兼容端点，无多 provider 冗余（架构锁使然，可接受但值得问）。

**阻塞点**：无。

## Reviewer B · 影视创作者

**走查路径**：Demo 四幕 → Scene 3 真实检索结果 → Scene 4 creative_support 输出。

**理解点**：
- 「为什么匹配」可见：`环境压过人物 / 纵深很深`——这正是选景时对 DP 说的语言，不是「相似图 0.87」。
- 跨媒介命中真实成立：同一查询下电影剧照与绘画并列，且理由相同——分镜找参考时非常有用。
- 方向统计（深空间 65%、主体居中 90%）能当视觉 Bible 的数据底稿。

**疑惑点**：
1. 检索输入要选 chips（结构化）而不是随便说一句话——自然语言只进 Assistant。Demo 中需说明这是刻意的（诚实、可解释），但初见会愣一下。
2. 「自己作品」能不能存？origin 有 ai-generated/user-upload 枚举，能存，但演示素材里没有（如实说明）。

**阻塞点**：无（上传 6MB 上限内、批量、失败可重试——工作流无卡点）。

## Reviewer C · 普通用户

**走查路径**：首页 → MEMORY → 空状态 → 上传 → 档案。

**理解点**：
- 从首页 04 卡「存下你的图，攒出你的视觉档案」知道 MEMORY 是什么（P5.8.2 修复后）。
- 空状态文案「电影剧照、绘画参考、随手拍都可以」直接对上素材直觉（P5.8.2 三用户全通过）。
- 「数据只存在你自己的浏览器」给了信任感。

**疑惑点**：
1. 「视觉语言」这个词第一眼抽象——需要 Demo 或空状态再降一点门槛。
2. 档案页四个 CTA（保存/按感觉寻找/我的视觉档案/Visual Assistant）信息量偏大，普通用户可能只点第一个。

**阻塞点**：无 D 类技术阻塞（P5.8.2/P5.8.3 连续两阶段 0 阻塞）。

## 汇总

| 评审 | 理解点 | 疑惑点 | 阻塞点 |
|---|---|---|---|
| A 工程师 | 架构/冻结/非 Agent 化 | 规则式召回上限、单 provider | 0 |
| B 创作者 | 为什么匹配、跨媒介、方向统计 | chips 输入非自由文本 | 0 |
| C 普通用户 | MEMORY 是什么、本地信任 | 「视觉语言」偏抽象、CTA 偏多 | 0 |

**表达侧结论**：无阻塞；两处疑惑（chips 的刻意性、术语门槛）已写进 Demo 脚本口播，展示时主动解释。
