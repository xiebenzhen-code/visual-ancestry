# P6.3.1 — Reasoning Control Capability Audit（只读审计）

**日期**：2026-10-08
**方法**：文档查证，**零API 调用、零代码修改**
**结论**：`REASONING_CONTROL_AVAILABLE = YES`（`reasoning_effort: "low"`）

---

## 0. 一句话结论

GLM-5.3 **思考无法关闭**（always-on），但**支持 `reasoning_effort` 三档 `low / high / max`**。
默认 `max` 是我们遇到的 `reasoning_content` 极长、
`content` 被挤空这一现象的直接解释。

**最小可验证参数**：`reasoning_effort: "low"`（顶层字段）。

---

## 1. 能力清单（按证据强度分级）

| 参数 | 分类 | 依据 |
|---|---|---|
| `reasoning_effort: "low" \| "high" \| "max"` | **OFFICIALLY_SUPPORTED** | 智谱官方模型文档 + API 参考 + 多家云厂商文档 |
| `thinking: { type: "enabled" }` | **OFFICIALLY_SUPPORTED**（但仅支持 enabled） | 同上 |
| `thinking: { type: "disabled" }` | **UNSUPPORTED — 会失败** | 官方明确说明；实测报HTTP 400 / error 1210 |
| `reasoning_effort: "none" \| "minimal" \| "medium" \| "xhigh"` | **UNSUPPORTED — 会失败** | 官方仅接受三档；实测 error 1210 |
| `thinking_budget` | **UNKNOWN / UNCONFIRMED** | GLM 官方文档未列；第三方网关称接受但忽略 |
| `enable_thinking: false` | **UNSUPPORTED** | GLM-5.3 模板不再读取该字段 |
| `response_format: json_schema` | **UNSUPPORTED（静默忽略）** | 见 §4，这是本次审计最重要的发现 |

## 2. OFFICIALLY_SUPPORTED

### 2.1 `reasoning_effort`

来源：`docs.bigmodel.cn/cn/guide/models/text/glm-5.3`（智谱官方）、`docs.z.ai/api-reference/llm/chat-completion`

| 值 | 语义 | GLM-5.3 是否接受 |
|---|---|---|
| `low` | 轻量推理 | ✅ |
| `high` | 增强推理 | ✅ |
| `max` | 深度推理 | ✅ **（默认值）** |

**默认 `max`** —— 我们此前从未显式设置，因此一直跑在最高档。
官方迁移说明明确写道：若原用 `thinking.type: "disabled"`，迁移到 GLM-5.3 应改为
`enabled` + `reasoning_effort: "low"`，**否则请求会失败**。

### 2.2 `thinking.type`

官方原文：**「仅支持开启思考，不支持禁用思考」**。
`enabled` 是唯一合法值，且已是默认。

### 2.3 跨厂商一致确认

| 来源 | 表述 |
|---|---|
| 智谱官方（bigmodel.cn） | 三档 `low/high/max`，默认 `max`，不再支持禁用 |
| Z.AI 官方（z.ai） | `reasoning_effort` 支持 GLM-5.2 及以上；GLM-5.3 只支持 `low/high/max` |
| 腾讯云 MaaS | 「此参数仅 glm-5.2 / 5.3 / 5.3-flash / 5.3-flashx 支持，默认 `max`」 |
| 百度智能云 | 「传 `low` 或 `high` 则不输出 `reasoning_content`」 |

> 百度那条尤其关键：**`low` 档下 `reasoning_content` 为空**，
> 意味着 reasoning 不再与 `content` 争抢 `max_tokens` 预算。

## 3. UNSUPPORTED（会失败，不是静默降级）

| 尝试 | 结果 |
|---|---|
| `thinking: {type:"disabled"}` | HTTP 400 / error **1210** |
| `enable_thinking: false` | 同上|
| `reasoning_effort: "none"` / `"minimal"` / `"medium"` / `"xhigh"` | 同上 |

error 1210 文案（多方实测一致）：
> `this model always thinks, turning thinking off is not supported; use low, high or max`

**这一点很重要**：关闭思考的路径**会大声失败**，不会被静默忽略。
所以「关掉 reasoning」不是本项目的可用方案。

---

## 4. 本次审计最重要的发现：`json_schema` 不被支持

这与我们的实测**高度吻合**，且此前从未被识别为根因。

### 4.1 多方独立实测

| 来源 | 观测 |
|---|---|
| synthorai.io | 对 GLM-5.3 送 strict `json_schema`，**16/16 次返回 HTTP 200 但忽略 schema**，输出裹在markdown 代码围栏里，且带schema 未要求的字段 |
| mcpplaygroundonline.com | GLM-5.3 用 strict schema **0/3 有效**；同条件 GLM-5.2 **3/3 有效** |
| OpenRouter 元数据 | GLM-5.2 列出 `structured_outputs`；**GLM-5.3 不列** |
| empiriolabs.ai | 「结构化输出是 JSON 模式，不是 schema 强制……提供 JSON Schema 会被接受但不强制执行」|
| Z.AI 官方 API 参考 | `response_format` 只列 `text` 与 `json_object` |

官方措辞：**「the trap is that the schema is accepted silently」**
—— schema 被接受，但静默不生效。

### 4.2 这解释了我们的历史观察

回看 P6.3.1 早期实测：1×1 像素探针返回
`subject_type` / `body_part_visible` / `weather` / `visual_style` 等 10 个字段，
与我们的 schema **零交集**。

**当时我判为「provider 忽略 json_schema」。现在有了更强解释**：
GLM-5.3 根本不执行 json_schema，它按自己的理解编字段名。
而 direct C 能返回 22 个正确字段，是因为 **SYSTEM_PROMPT 里用自然语言
逐条列出了字段与枚举** —— 起作用的是 prompt，不是 schema。

> 这也解释了为什么 direct C 有时成功、有时失败：
> prompt 引导 + always-on reasoning 双重压力下，
> `max_tokens` 小的样本会被 reasoning 吃光。

**修正后的认识**：`json_schema` 在 GLM-5.3 上从未生效过。
bridge 当前依赖它来保证 22 字段结构，**这个假设不成立**。

## 6. 异常登记：`PROVIDER_USAGE_ACCOUNTING_OR_ROUTING_ANOMALY`

### 6.1 实测数据（`work/p6.3.1c/max-tokens/max-tokens-d1d2.json`）

| 探针 | HTTP | `finish_reason` | `completion_tokens` | `reasoning_content` 长度 | `content` 长度 | schema-valid |
|---|---|---|---|---|---|---|
| **D1**（`max_tokens=800`） | 200 | `stop` | **395 / 800** | 605 | 605 | **true** |
| **D2**（`max_tokens=1600`） | 200 | **`length`** | **1600 / 1600** | **3 462** | **0** | — |

**输入字节完全相同**（同一张 `monk-by-sea/detail.webp`），
schema 与 SYSTEM_PROMPT 亦逐项一致，仅 `max_tokens` 不同。

### 6.2 异常一：`prompt_tokens` 相差 5.66倍

| 探针 | `prompt_tokens` |
|---|---|
| D1 | **1 499** |
| D2 | **265** |

**分类：`PROVIDER_USAGE_ACCOUNTING_OR_ROUTING_ANOMALY`**

**不猜原因。** 可能涉及缓存计费口径、路由到不同后端、或 usage 统计差异 ——
当前**无任何观测数据**可区分这些假设。

**影响**：`usage` **暂不可作为稳定因果证据**。
此前把 `completionTokens = 749/800` 当作「预算临界」的量化依据，
在 usage 不可靠的前提下**降级为参考性观测**。

### 6.3 异常二：`content` 与 `reasoning_content` 长度完全相同

D1 的两者**均为 605**。这意味着 D1 这次返回中，
`content` 与 `reasoning_content` 可能是**同一段文本的两个副本**，
而非「推理 605 字符 + 回答 605 字符」。

**分类：`PROVIDER_RESPONSE_SHAPE_ANOMALY`（仅登记，不推断成因）**

> 这一项需要 D1/D2 原始响应体才能进一步确认，本次审计**未取原始体**。

### 6.4 当前 verdict（来自实测，非本审计结论）

```
MAX_TOKENS_SINGLE_CAUSE_EXPLANATION = REJECTED
```

D2 在双倍预算下仍被 reasoning 吃光（`1600/1600`，`content_len=0`），
**max_tokens 单因解释已被证伪**。
这与 §7 的机制解释一致：真正的变量是 **reasoning 档位**，不是 token 预算总量。

---

## 7. 关于「提高 max_tokens 不是可靠修复」

同意该结论，实测数据给出了机制层面的解释：

| 证据 | 含义 |
|---|---|
| D2 `max_tokens=1600` → `completion_tokens=1600/1600`、`finish_reason=length`、`content_len=0`、`reasoning_len=3462` | 即使加倍预算，仍被 reasoning 吃光 |
| verdict = `MAX_TOKENS_SINGLE_CAUSE_EXPLANATION = REJECTED` | **max_tokens 单因解释已证伪** |
| 默认档位是 `max` | 我们一直跑在最高 reasoning 强度 |
| `low` 档下 `reasoning_content` 为空（百度文档） | **降低 reasoning 才是有效方向**，而非加预算 |

因此修复方向从「加token」转为「**降 reasoning 档位**」。

> D1 这次只用了 395/800 就成功，说明 **800 预算并非必然不足** ——
> 变量是 reasoning 长度，而reasoning 长度受档位影响。
> 这也解释了为什么同样的请求有时成有时败。

## 8. 结论

```
REASONING_CONTROL_AVAILABLE = YES
```

**最小可验证参数**（若确认走桥）：

```json
{
  "reasoning_effort": "low"
}
```

顶层字段，与 `model` / `temperature` / `max_tokens` 同级。

### 建议的验证顺序（尚未执行）

1. **先验证 provider 是否透传** —— 这是唯一的前置未知项。
   最小成本做法：先发一个**不涉及图片**的 text-only 请求，
   对比 `reasoning_effort: "low"` 与 `"max"` 的 `completion_tokens` 差异。
   若无差异，说明该层未透传，方案不成立。
2. 透传确认后，再对 painting 做单变量验证。
3. 由于 `json_schema` 已确认不被支持（§4），
   **结构保证必须改由 SYSTEM_PROMPT + 客户端校验承担**，
   这与已登记的 `docs/P6.3.1-schema-validation-gap.md` 是同一件事。
