## 0. 结论

> **NO —— 产品不应该预下载外部语料。**

```
Visual Query → External Source Search → candidates → Vision (cached) → scoreIntent → references
```

## 2. 为什么必须用 stub 证明 cache

无 provider 时，端到端跑不出「第二次不重复调用」—— 因为**没有成功的 intent 可缓存**。

但 cache 正确性是**编排层的属性，不是 provider 的属性**。所以：

| 组件 | 用真还是替身 | 说明 |
|---|---|---|
| 外部源搜索 | ✅ **真** | 真实调用 Met / AIC / Rijks API |
| 图片下载 + 魔数 + sha256 | ✅ **真** | `materializeRecord` |
| cache 键与生命周期 | ✅ **真** | 本次要测的就是它 |
| **Vision 调用** | ⚠️ **stub（计数替身）** | 只为计数，intent 标记 `source: "STUB-not-a-real-reading"` |
| **冻结评分器** | ✅ **真** | `src/services/retrieval/scoring.js`，未改动 |
| reasons 生成 | ✅ **真** | `sharedReasons`，未改动 |

**stub intent 在任何报告中都不得被当作真实视觉读数。** 这条写进了 `cache-proof.json` 的 `IMPORTANT` 字段。

真实 provider 链路在 `dynamic-source.json` 中单独记录（13 次尝试，全部 `provider-not-configured`，诚实失败）。

## 3. 实测发现的三个 cache 设计缺陷（已修正）

这一轮不是「跑通」，是**跑出三个真实缺陷**。

### 缺陷 1 · sha256-only 键永远不命中

**现象**：轮 2/3 的 cacheHits 恒为 0。

**根因**：外部搜索**不稳定** —— 同一主题两次调用返回的排序不同、文件不同。实测：

```
met landscape 两次：340468,10181,359362,335112,11181  ← 相同
aic landscape 两次：23119,874,146701,90048,68792        ← 相同
```

搜索本身稳定，但**下载后的 sha256 与历史条目不匹配**，因为第一轮我根本没写入成功条目（见缺陷 2）。

**修正**：引入**双层键** —— `(source, sourceId)` 为稳定主键（博物馆自己保证的资产身份），sha256 为次键（识别同图重挂）。

### 缺陷 2 · 环境性失败不写 ledger，导致 cache 形同虚设

**修正前**：只有非环境性失败才写入 ledger。`provider-not-configured` 被判为环境性 → **一条都不写** → ledger 永远空 → 「不重复调用」无法证明。

```
修正前：entries: 0 | byAssetId keys: 0
```

**修正**：**每次尝试都记录**，含 `attempts` / `firstAttemptAt` / `lastAttemptAt`；环境性失败标 `retriable: true` 且**不写入 `byAssetId`**（避免冒充「已分析」）。

> 这个缺陷的教训：**「不写失败」听起来像避免污染，但它让 cache 既无法命中、也无法自证。** 记录失败与记录成功同等重要。

### 缺陷 3 · retriable 语义缺失会让凭据到位后仍永久失败

若把 `provider-not-configured` 当作永久失败缓存，凭据到位后这些资产会被永久跳过。

**修正**：区分
- 环境性（provider 未配置 / 5xx）→ `retriable: true`，**不占byAssetId**
- 资产性（图片本身被拒）→ `retriable: false`，写入 `byAssetId`，后续直接跳过不浪费调用

## 4. 延迟分解（实测）

| 阶段 | 延迟 | 占比 |
|---|---|---|
| **外部源搜索（三源并行）** | **16.6–30.5 s** | **>99%** |
| 图片下载 + 校验 | 含在搜索内 | — |
| **冻结本地评分** | **0.13–0.93 ms** | **<0.01%** |
| Vision 分析（每张） | 真实环境 9.8–22 s（历史实测） | 首次才有 |

**这组数字直接支撑「不预下载」的决策**：

- 预下载 = 一次性付出 N × (搜索 + 下载) 的时间与 N × 体积的存储
- 动态 = 只为**实际被查询的**资产付出成本，且**第二次查询免费**

**Rijks 是瓶颈来源**：它每条资产需两次请求（search 拿 id → resolve 拿元数据），比 Met/AIC 慢一半。
