## 2. Contract Probe — HTTP 200，但暴露严重问题

按既定顺序先跑 `work/p6.3.1c/contract-probe.mjs`。

### 2.1 A. text-only（契约确认）

```
HTTP 400 · 62 ms · error.code = missing-field
→ bridge 强制要求 imageBase64 + mimeType（设计如此）
```

### 2.2 B. 1×1 像素 PNG（最小真实请求）

```
HTTP 200 · 11650 ms · ok = true · bridge 内部 latencyMs = 11624
intent = {
  "subject_type": null,        "body_part_visible": null,
  "spatial_arrangement": null, "interaction": null,
  "scene_type": null,          "weather": null,
  "setting": null,             "text_visible": null,
  "face_visibility": null,     "visual_style": null
}                ← 10 个字段
```

### 2.3 硬证据：字段名与冻结 schema 无交集

| 侧 | 字段 |
|---|---|
| **provider 实际返回（10）** | `subject_type` · `body_part_visible` · `spatial_arrangement` · `interaction` · `scene_type` · `weather` · `setting` · `text_visible` · `face_visibility` · `visual_style` |
| **bridge 请求的 schema（22）** | `subject` · `subjectScale` · `subjectPosition` · `spatialDepth` · `negativeSpace` · `environmentDominance` · `lightDirection` · `lightQuality` · `colorTemperature` · `saturation` · `contrast` · `humanRelation` · `cameraDistance` · `cameraHeight` · `cameraRelation` · `motion` · `visualDensity` · `arousal` · `socialDistance` · `melancholy` · `emotion` · `atmosphere` |
| **交集** | **0个** |

源码依据 `server/vision/openaiProvider.mjs:94-121`：
`buildSchema()` 由 `ENUM_FIELDS` 生成，`required` 覆盖全部字段，
`additionalProperties: false`，`strict: true`，
并在 `:291` 以 `response_format: { type: "json_schema" }` 发往上游。

**字段名完全错位= 上游忽略了 json_schema 约束，自行编了一套字段。**
这是结构级证据，与图片内容无关。

### 2.4 为什么客户端会直接收到错字段

`scripts/server.mjs:121`：

```js
sendJson(res, 200, { ok: true, intent: result.raw, latencyMs: result.latencyMs ?? null });
```

`result.raw` 是 `JSON.parse(content)` 的**原始产物**，bridge **不做白名单归一化**。
所以上游编错字段 → 直接透传给浏览器。这是数据通路事实，不是推测。

### 2.5 `CHAT_COMPLETIONS_CONTRACT = NOT_CONFIRMED` 的正确解读

探针检查 `choices[] / message.content / finish_reason / usage`，全部为 `null`。
**这不是 provider 故障，而是探针的可见性局限**：
`scripts/server.mjs:121` 只返回 `{ ok, intent, latencyMs }`，
`choices[]` 从未暴露给客户端（源码核对确认）。

| 字段 | 值 | 是否代表provider 异常 |
|---|---|---|
| `choices[]` | `null` | ❌ 否 —— bridge 不透传 |
| `finish_reason` | `null` | ❌ 否 —— 同上 |
| `usage` | 未提供 | ❌ 否 —— 同上 |
| **`intent` 字段名** | **错位** | ✅ **是** —— 这才是真信号 |

>教训：探针报NOT_CONFIRMED 时，必须回到源码确认「这个字段本来能不能看到」。
> 否则会把「bridge 不暴露」误判成「provider 不支持」。

## 4. 精确分类：`PROVIDER_EMPTY_CONTENT`

**分类链路（每一环都有源码依据）**：

```
上游返回 HTTP 200（认证已通过，请求真实抵达）
  → JSON.parse(text) 成功            openaiProvider.mjs:166
  → content 非字符串或为空            openaiProvider.mjs:181
  → outcome(false, "empty-response") openaiProvider.mjs:196
  → HTTP 502 + error.code            scripts/server.mjs:118
  → 分类器读 error.code（本轮已重写）
  → PROVIDER_EMPTY_CONTENT
```

**对照taxonomy 六分类**，本轮**不适用**项逐一排除：

| 分类 | 排除依据 |
|---|---|
| `SERVER_NOT_RUNNING` | 4175 OPEN 1 ms，HTTP 200 |
| `PROVIDER_AUTH_FAILED` | **已解除** —— 本轮从 `auth` 变为 200 |
| `PROVIDER_MODEL_UNSUPPORTED` | 模型确实被调用（有响应体、有延迟） |
| `PROVIDER_INVALID_JSON` | `JSON.parse` 成功，非语法错误 |
| `PROVIDER_TIMEOUT` | 24.9s / 47.8s < timeout 阈值（未超时） |
| `BRIDGE_CONTRACT_ERROR` | 请求体合法（图像 mime 在白名单内） |
| **`PROVIDER_EMPTY_CONTENT`** | ✅ **精确命中** |

## 5. 关键反证：1×1 成功，真实照片失败

| 输入 | 结果 |
|---|---|
| 1×1 空白像素 | **HTTP 200**，返回 200 但字段错、全 null |
| 真实绘画 1920×1221 | 502 `empty-response` |
| 真实电影帧 2480×1825 | 502 `empty-response` |

这个反差排除了「凭据 / 网络 / 模型不可用 / 端点错误」——请求链路完全通畅。
它指向**同一个根因的两种表现**：上游不执行 schema 约束。
真实图片让模型尝试填满 22 个必填枚举字段，它做不到 → 返回空 content；
空白图无内容可填 → 给出编造的字段名 + 全 null。

**两者是同一缺陷的两个症状，不是两个独立问题。**

## 9. 根因与下一步（需用户决策）

**根因**：上游不遵守 `response_format: { type: "json_schema", strict: true }`。
责任在上游，不在本项目的bridge 契约、载荷形状、schema 定义或评分逻辑。

**下一步存在分叉，且都涉及「是否允许改bridge」，故未擅自行动：**

| 方案 | 做法 | 对「不改bridge」的影响 |
|---|---|---|
| A | 改用 `json_object` 模式 | 需改 `requestBody()`（bridge 内） |
| B | 去掉 strict，schema 内联进 prompt | 需改 `requestBody()` + SYSTEM_PROMPT（bridge 内） |
| C | 更换 provider | ✅ **零代码改动**，仅换环境变量 |

> `buildSchema()` 与 `requestBody()` 都位于 bridge 内，因此 A / B 都会修改 bridge。
> 若坚持零bridge 改动，只有 C 可行。

**另一条独立线索**：bridge 内有`[vision-debug]` 日志会打印上游响应前 200 字符
（`openaiProvider.mjs:158-162`）。用户侧 server 进程的 stdout 可取到
`finish_reason`、`refusal`、`usage` 等本报告无法获得的字段 ——若上游是因
`content_filter` 拒绝或 `length` 截断而返回空，日志里会有直接证据。
需要用户从运行 server 的 PowerShell 窗口拷贝这几行。

## 11. 方法论沉淀

1. **探针自校准**：先连一个确定开放的端口证明探测方法有效，再测目标端口。
   否则「端口关闭」与「代理代答」不可区分。
2. **NOT_CONFIRMED 要回源码复核**：探针报字段缺失时，先确认该字段是否本就不
   对客户端暴露。本轮 `choices[]`缺失是 bridge 设计，不是 provider 故障。
3. **错误分类读 `error.code` 而非外层 HTTP**：bridge 把所有 provider 侧失败
   统一映射为 502，只看外层状态码无法区分 auth / quota / empty / timeout。
4. **反证法定位根因**：1×1 成功而真实图片失败，这个反差一次性排除了凭据、
   网络、模型、端点四类原因。
5. **字段名错位是结构级证据**：与图片内容无关，比「值是null」更强——
   空白图本就该全 null，但字段名不会因此改变。
